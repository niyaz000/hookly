# ADR api-design/002: Dual ID strategy — internal UUIDv7 and public prefixed NanoId

## Status
Accepted

## Context

Every resource stored in the database needs an identifier. That identifier is used in two distinct contexts:

1. **Database operations** — primary key for joins, index seeks, and keyset pagination (see [ADR 001](001-cursor-pagination.md))
2. **API surface** — identifies resources in URL path segments, request bodies, and response payloads

A single identifier must serve both roles unless the two contexts are deliberately separated. The choice of identifier has significant implications for security, performance, and developer experience.

### Why not auto-increment integers?

Sequential integers are the simplest choice, but they expose three problems:

**Enumeration.** `GET /api/v1/applications/1`, `/2`, `/3` … lets any caller walk the entire resource space without authorization hints. Nothing about the ID format signals where the range ends.

**Information leakage.** ID `5000` tells clients there are approximately 5 000 applications in the system. Two requests separated by a day reveal the creation rate. For a multi-tenant platform, this is a competitive intelligence leak.

**No cross-system portability.** In a sharded or distributed deployment, sequences require a global coordinator to avoid collisions — a single point of contention. UUIDs sidestep this entirely.

### Why not expose UUIDv7 directly?

UUIDv7 is an excellent primary key: its 48-bit millisecond timestamp prefix makes it monotonically increasing, which keeps B-tree index inserts sequential and enables keyset pagination. But exposing it as the public API ID creates two problems:

**Creation-time leakage.** UUIDv7 embeds a wall-clock timestamp in its most-significant bits. A client can extract the approximate creation time of any resource from its ID — including resources belonging to other tenants that happen to appear in cross-tenant references.

**Ordering leakage.** Because UUIDv7 values are monotonically increasing, clients can determine which resource was created first by comparing IDs lexicographically. This reveals platform activity patterns and relative resource age.

### Why not UUIDv4?

Random UUIDv4 avoids both leakage issues. But it has a different cost:

**Index fragmentation.** Random UUIDs scatter new rows throughout the B-tree on insert, causing page splits and leaving pages partially full. At table sizes typical for `events` and `delivery_jobs`, this compounds into measurable write amplification and bloat. UUIDv7's sequential property eliminates this entirely — new rows always append to the rightmost leaf page.

### The dual-ID solution

Maintain two identifiers per row:

- **`id` (UUIDv7)** — internal primary key, never surfaced in the API
- **`public_id` (prefixed NanoId)** — the only identifier clients ever see or use

The internal key is optimized for the database. The public key is optimized for the API surface. The two concerns do not need to compromise.

## Decision

Every resource table carries two identifier columns:

| Column | Type | Role |
|---|---|---|
| `id` | `UUID` | Internal PK, generated as UUIDv7 — monotonic, index-efficient, keyset cursor |
| `public_id` | `VARCHAR` | Public API identifier — prefixed NanoId, opaque, URL-safe, never used in joins |

**Format:**
```
<prefix>_<NanoId>

app_Xk9mN4rTpQzH7wLs    ← application
ep_Ym7bK3vWsRjF9tPnc    ← endpoint
evt_Zn3dL8uXqMgE2aSo    ← event type
```

**Resource prefix table:**

| Prefix | Resource |
|---|---|
| `app_` | applications |
| `ep_` | endpoints |
| `sec_` | endpoint secrets |
| `evt_` | event types |
| `evn_` | events |
| `dj_` | delivery jobs |
| `org_` | organizations |
| `ten_` | tenants |
| `usr_` | users |
| `tea_` | teams |
| `mem_` | team members |
| `inv_` | invites |
| `sch_` | schedules |
| `sxe_` | schedule executions |
| `jwk_` | JWT keys |
| `kid_` | JWT key IDs |
| `key_` | API keys |
| `aks_` | API key scopes |
| `rol_` | roles |
| `per_` | permissions |
| `env_` | environments |
| `pwh_` | platform webhooks |

**Rules:**
- `id` is never returned in API responses and never accepted in API requests
- `public_id` is used in all URL path segments (`/api/v1/applications/app_Xk9...`) and in all cross-resource references in request and response bodies
- `public_id` carries a `UNIQUE` constraint; lookups by `public_id` resolve to the internal `id` at the repository layer before any joins or further operations
- The NanoId component is generated by a CSPRNG — clients must treat `public_id` as an opaque token with no decodable structure

For the entropy analysis and length selection of the NanoId component see [ADR 009](009-public-id-length.md).

## Principles upheld

- **Security by design** — opaque public IDs are non-enumerable: knowing `app_Xk9mN4rTpQzH7wLs` reveals nothing about adjacent resource IDs, total resource count, or creation time
- **Performance as first-class** — UUIDv7 as the internal PK delivers sequential B-tree inserts with no page splits; keyset pagination anchors on the ordered `id` column, never on `public_id`
- **Developer experience** — type prefixes give instant visual context in logs, errors, and debuggers; `dj_Zn3dL8uX` is immediately recognizable as a delivery job without consulting documentation

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Sequential integer, exposed as API ID | Enumerable; leaks total row count and creation rate; requires global coordination in sharded deployments |
| UUIDv4 as single ID (internal PK + public) | Random UUIDs fragment B-tree indexes; 36-char hyphenated representation is verbose in URLs; no resource-type prefix |
| UUIDv7 as single ID (internal PK + public) | Embeds a 48-bit millisecond timestamp — clients can extract creation time and observe ordering; couples the API contract to the internal timestamp format |
| Prefixed NanoId as both PK and API ID | Random IDs as B-tree PKs cause page splits and index bloat at scale; cannot serve as a keyset cursor (no ordering guarantee) |
| Hash-based ID (HMAC of internal PK) | Deterministic — anyone knowing the key and internal PK can reconstruct the public ID; no entropy advantage over a random ID |

## Consequences

**Positive:**
- Clients cannot enumerate resources or infer creation time or ordering from public IDs
- Internal schema changes (e.g., different UUID generation strategy) are non-breaking: `public_id` is an independent API contract
- Type prefix makes IDs self-describing in logs, errors, and cross-service references without documentation lookup
- B-tree index performance is maintained at any table size: UUIDv7 inserts are sequential

**Negative:**
- Every resource lookup crosses two identifiers: `public_id → id` resolution at the repository layer adds one indexed lookup per request
- Schema carries an extra column and a `UNIQUE` index per resource table
- The prefix registry is an implicit convention; there is no enforced registry preventing two resources from accidentally sharing a prefix
